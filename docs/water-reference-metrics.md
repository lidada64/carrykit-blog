# 水面视觉标尺 (W0) — 指标定义、基线与用法

> 状态:2026-09-02 完成。这把尺子是 `docs/` 里「灯球照水」计划 W0 的产出,
> **W2~W9 每一张任务卡的验收都跑它**,不再靠肉眼说「看着还行」。
> 相关:`scripts/water-metrics.mjs`(评分器)、`scripts/water-harness.mjs`(黄金帧渲染台)。

---

## 1. 为什么需要一把尺子

「像不像奥伯拉丁 / 像不像那张照片」如果不落成数字,多个人(或多个 agent)并行调参时
无法收敛:每个人心里的「像」不一样,而且改一处参数往往按下葫芦浮起瓢。把参考图量化成
8 个指标之后,收活变成一次跑分,PR 里贴的是分数表而不是形容词。

尺子本身也必须可复现,所以三张参考图缩到统一尺寸后**入库**在 `docs/water-refs/`
(共 ~800KB),任何人都能 `npm run water:baseline` 复算一遍。

---

## 2. 分析约定

固定这些约定,否则不同分辨率、不同 dpr 的图之间不可比:

| 项 | 约定 | 理由 |
|---|---|---|
| 分析分辨率 | 统一缩到**高度 1200px、保持宽高比** | 以 px 计的指标(波长、划线长度)需要共同基准;高度归一才让分带统计对齐 |
| 去趋势 | 减掉 **41px 盒模糊** | 只留波纹这一档的局部结构,大尺度明暗(天光、岸影)不参与 |
| 分带 | 屏幕高度均分 **10 带**,band 0 = 顶端 = 远 | 对比度沿景深的分布是核心判据 |
| 带内展度 | 每列 RMS 的 **40 分位数**,不是整带 RMS | 见 §4 的坑 1 |
| 1-bit 输入 | 先局部平均**反抖动**还原密度场再统计 | 见 §4 的坑 2 |
| 特征侧 polarity | `near`/`mid` = 暗划线,`obra` = 亮墨点 | 跟着 baseline 走,不自动猜 |

## 3. 八项指标

| 指标 | 权重 | 定义 | 抓的是哪种失败 |
|---|---|---|---|
| `foregroundFlatness` | **0.20** | 末两带展度 / 峰值带展度 | 把最大对比度堆在前景——最常见、最致命 |
| `coherence` | **0.20** | 峰值带结构张量 (λ₁−λ₂)/(λ₁+λ₂) | 波纹退化成各向同性噪点,读作沙子不是水 |
| `curveCorrelation` | 0.15 | 归一分带曲线与基线的皮尔逊相关 | 亮度沿景深的整体分布跑偏 |
| `peakBand` | 0.10 | 峰值所在带 0..9 | 掠射带位置错(逆投影或地平线设错) |
| `dashAspect` | 0.10 | 特征游程 宽/高 中位数(按对比度够的几带取中位) | 暗部是圆点不是短划 |
| `gradAngleDeg` | 0.10 | 主梯度角,归一到 [0,180),90 = 横向条纹 | 风向参考系接错 |
| `featureCoverage` | 0.10 | 峰值带特征像素占比 % | 整体过曝或过暗 |
| `gridArtifact` | 0.05 | 高频段(>0.4×Nyquist)落在孤立谱峰上的能量占比 % | 有序抖动(Bayer)的网纹残留 |
| `spectralLineiness` | 0.05 | 波段(<0.4×Nyquist)谱平坦度的补:1 − 几何均值/算术均值 | 少量固定正弦织出的**周期性点阵**(判别力弱,见 §4 坑 5) |

**加权总分 ≥ 0.80 视为达标。** 某项基线为 `null` 时不计分,其余权重按比例归一。

### 为什么 foregroundFlatness 权重最高

三张参考图的分带对比度**全是单峰**:峰落在「掠射角使 Fresnel 反射率陡升」与
「波长仍可分辨、未被逐像素平均」两个条件的交点上;最靠近相机的前景只有峰值的
0~7%,因为那里视角最陡、F0≈0.02 的菲涅耳反射率极低,看进的是水体而不是天空,
水面读作玻璃。

而绝大多数水面 shader(**包括本仓库改造前的 `water-dither.tsx`**)把最大对比度
堆在离相机最近的地方,方向正好反了。这一项一票否决。

## 4. 造尺子时踩到的坑(全部改变了算法)

> 坑 1、2 是造尺子时发现的;坑 3、4、5 是 W1 拿它给**量化后的渲染输出**打分时才暴露的
> ——只跑参考图看不出来。

### 坑 1 · 整带 RMS 会被一条窄亮光路带偏

第一版用整带 RMS 当展度,结果奥伯拉丁那张的 `foregroundFlatness` 量出 **0.51**,
看起来「前景一点也不平」——与结论矛盾。查下去发现:画面下缘有一条又窄又亮的
**月光路径**(镜面高光打穿了平静的前景),整带 RMS 被它抬起来了。

环境水面的平静与镜面光路的明亮是**两件事**,这条指标只该量前者。改成取
**每列 RMS 的 40 分位数**:忽略掉少数被光路占据的列,量的是「典型一列有多静」。
对没有窄亮特征的照片类参考,它与整带 RMS 几乎一致(near 0.112→0.030,mid 0.072→0.065),
而奥伯拉丁降到 **0.00**,三张参考这才一致。

> 对后续任务卡的含义:**灯球在水面投下的光斑不该被算作「前景不平」的证据**。
> 光斑该亮,环境水面该静,两者并存才是对的。

### 坑 2 · 直接对 1-bit 图算局部 RMS,量到的是抖动噪声

奥伯拉丁截图是硬 1-bit(81.1% 像素是一个暗色 `#32331A`,3.8% 是一个亮色 `#E6FEFD`)。
对它直接算局部 RMS,只要有墨点的地方 RMS 就一样高,分带曲线整片糊平,
`featureCoverage` 量出 15.5% 而不是实际的 36.6%。

改成先检测「有效 1-bit」(两个色调覆盖 ≥85% 像素),然后:
- **field**(用于分带展度 / 相干度 / 波长)= 二值图的 9px 局部平均,**反抖动**还原出量化之前的密度场;
- **ink**(用于 `dashAspect` / `gridArtifact`)= 二值墨点本身。

改完 `featureCoverage` 36.6%(基线 36.8%)、`gradAngle` 90.2°、曲线相关 0.979。

> 这一步不是为了迁就参考图——**我们自己的产出也是 1-bit 抖动输出**,不做反抖动
> 就没法给自己打分。

### 坑 3 · 缩放之后再做 1-bit 判定,判定必然失效

第一版在解码时就把图缩到分析高度,再判 bilevel。对 1-bit 渲染输出这是致命的:
插值把两个色调抹成连续灰阶,bilevel 判定不成立 → 整幅图按连续图统计 →
量到的全是抖动噪声,分带曲线糊平、相干度归零(实测 0.01~0.03)。

改成:**在原生分辨率上判定并反抖动**,再把还原出的密度场面积平均降采样到分析高度;
`dashAspect` 与 `gridArtifact` 所需的墨点掩码**始终留在原生分辨率**上量。

### 坑 4 · 墨点在哪一侧不能自动猜

bilevel 分支原本按「少数色调即墨点」自动判断。渲染输出整体偏暗时会猜反:
`featureCoverage` 直接量到 60%+(实际应为 20% 左右)。改成**听 baseline 指定的
polarity**(near/mid 看暗划线,obra 看亮墨点),不再自动猜。

### 坑 5 · 第 9 项指标是 W1 用眼睛发现的,而且它判别力偏弱

W1 的第一版波场用 6 个固定正弦,跑分 **0.970**,但画面是织成布纹的**周期性干涉点阵**
——相干度、游程、梯度角、谱尖峰度全都看不出周期性。于是补了 `spectralLineiness`
(波段谱平坦度的补)。

诚实说明它的局限:点阵实测 29%,三张参考 16~22%,**判别间距很小**;而且在
「大片平底 + 一条窄暗带」这类构图上会误报(mid 量化帧报 88%)。所以权重只给 0.05,
**当告警用,不当门槛**。真正可靠的防线是下面这条流程要求。

### 由此定下的流程红线

**分数只能证伪,不能证真。** 每张卡的 PR 除了分数表,必须附黄金帧本身,
且提交人要真的看过。W1 过程中「分数达标但画面是错的」出现了 **3 次**
(周期点阵 0.970、蓝噪声秩排布有簇 0.952、抖动淹没结构),
每一次都是靠肉眼发现、而不是靠分数。

### 附带修正 · `dashAspect` 没有全局目标

原计划写的是「≥2.5」。实测发现横向拉长是**中景那一档**的特征(3.5),
近景特写在峰值带本就接近方形(1.5),奥伯拉丁用的是各向同性抖动(1.0)。
所以改成按各自 baseline 的值打分,相对误差 40% 以内满分。

## 6. 改造前的 `water-dither.tsx` 跑分

黄金帧:`golden/baseline/current-t{0,1.0,2.5,5.0}.png`(1920×1080, dpr=1, 固定 uTime)。
对照 `mid` 基线:

| 指标 | 实测 | 基线 | 判定 |
|---|---|---|---|
| foregroundFlatness | 0.356 | 0.065 | **FAIL** |
| coherence | **0.003** | 0.974 | **FAIL** |
| curveCorrelation | 0.579 | 1 | WARN |
| peakBand | 2 | 4 | WARN |
| dashAspect | 1.0 | 3.5 | **FAIL** |
| gradAngleDeg | 44.4 | 91.7 | **FAIL** |
| featureCoverage % | 20.5 | 19.6 | PASS |
| gridArtifact % | **64.37** | 0 | **FAIL** |
| **加权总分** | **0.274** | — | **未达标** |

分带 RMS `[17.1, 61.0, 66.7, 46.4, 34.5, 31.1, 16.3, 18.7, 17.5, 29.9]`
——峰在 band 2、前景又翘起来,是「双峰 + 前景不静」,与参考的单峰完全不同。

**读数**:

1. **相干度 0.003** 几乎是完美的各向同性。双层域扭曲 `uWarp*(0.42·warp1+0.22·warp2)`
   加 `flowBend*11.0` 的相位扰动把波脊揉成了噪声,梯度角 44.4° 说明连一个主方向都没有。
   → W2 要把扰动强度降到相干度 ≥0.85。
2. **谱尖峰度 64.37%** —— 高频能量的三分之二住在 Bayer 8×8 的网格谐波上。
   `NEXT.md` 里那句「满屏纸碎屑」现在有了数字。→ W4 换蓝噪声。
3. **前景平坦度 0.356 + 峰值带在 2** —— 没有逆投影、没有 Fresnel,
   对比度既不压缩也不成带。→ W2 的透视映射 + W3 的菲涅耳。
4. 唯一及格的是 `featureCoverage`(20.5% vs 19.6%),说明整体曝光是对的,
   问题全在结构而不在明暗。

## 7. 用法

```bash
npm run water:baseline                    # 自检:对三张参考图复算,验证尺子没漂
npm run water:metrics -- <img> --baseline near|mid|obra [--json]
npm run water:frame -- --shader <f.frag|.glsl.ts> --out golden/x.png --time 2.5 [--cost]
```

`water-harness.mjs` 固定 1920×1080 / dpr=1 / `uTime` 由 `--time` 显式给定
(**绝不用 `performance.now()`**)/ `preserveDrawingBuffer`,这是计划 §5 的黄金帧协议。
它同时探测 WebGL2 能力并打印渲染器名。

### 一个必须知道的限制

本项目的云端开发容器没有 GPU,headless Chromium 走 SwiftShader 软件光栅,
所以 `--cost` 报的是**软件光栅每帧墙钟时间**,只能做路线之间的**相对**比较
(软件光栅耗时随每像素 ALU 量增长,恰好是区分方案的那个量),**不是 GPU 预算值**。
真实 GPU 帧时间必须在有显卡的机器上用 `EXT_disjoint_timer_query_webgl2` 量,
这件事归 W9。

```bash
npm run water:bluenoise            # 生成抖动阈值图(自检会打印 5 个阈值下的残余 std)
```

改动 `water-metrics.mjs` 的任何算法后,必须重跑 `npm run water:baseline`
并把新值同步回脚本里的 `BASELINES`,否则所有卡的验收都会一起漂移。

## 8. W2 消融与摆动扫描(2026-09-03)

三件套(① 风阵斑块 / ② 长尾划线 / ③ 局部方向摆动)对 mid 基线总分的贡献:

| 配置 | 相干度 | dashAspect | 覆盖率% | 总分 | Δ |
|---|---|---|---|---|---|
| 三件套全关 | 0.778 | 2.00 | 21.0 | **0.758** | — |
| ① ② ③ 全开 | 0.851 | 1.67 | 28.1 | **0.820** | +0.062 |
| 只关 ① 斑块 | 0.743 | 2.00 | 19.3 | 0.699 | **−0.121** |
| 只关 ② 长尾 | 0.864 | 2.00 | 28.7 | 0.841 | **+0.021** |
| 只关 ③ 摆动 | 0.855 | 1.67 | 28.1 | 0.818 | −0.002 |

**读数:**

1. **全关 0.758 ≈ W1 spike 的 0.760** —— 模块化拆分没拆坏东西。
2. **① 斑块一个人扛了全部收益**(−0.121)。而且它同时改善相干度(0.743→0.851)与
   前景平坦度(0.328→0.222):镜面斑块本身就是"平静的前景",不需要额外机制。
3. **② 长尾划线目前是负收益**(关掉反而 +0.021)。但注意评分器**没有任何一项测"长度分布"**
   ——`dashAspect` 只看中位数,长尾抬的是方差。所以这条不能据此砍掉,
   要么给评分器补一项 `dashAspectP90/P50`,要么当成纯观感项由 W8 定夺。
4. **③ 摆动对分数几乎免疫**(−0.002)。

### 摆动 / 各向异性的交点:靠收窄方向散布买,不是靠压小摆动

用户原本的设想是"减小摆动频率与幅度来控制对各向异性的影响"。实测**摆动本身极便宜**:
幅度 0→0.45 全程只吃掉 0.029 相干度。真正卡住门槛的是**基线相干度本来就只有 0.855**。

| uFieldSpread | wander 0.10 | 0.30 | 0.45 |
|---|---|---|---|
| 0.50 | 0.851 | 0.841 | 0.826 |
| 0.35 | 0.868 | 0.858 | 0.847 |
| **0.25** | **0.870** | **0.861** | **0.855** |

收窄方向散布 0.5→0.25 买到约 +0.029 相干度,正好够把摆动从 0.10 推到 0.45 还留在门槛之上。

**默认取 spread 0.25 / wander 0.30**(相干度 0.861,总分 0.818)。
wander 0.45 分更高(0.840),但**肉眼看会拉出几条几乎笔直贯穿全幅的长划,反而假**
——又一次"分数偏爱、眼睛不同意"。最终取值留给 W8 的调参环节定。

### 9.1 三条从「像素→物理」反推出来的量

1. **环境列的树线边界该落在反射仰角 0.33,不是地平线的 0.0。**
   mid 构图(1.6m 机位、俯角 0.37、fov 0.61)的地平线在 ndc.y=1.234,**在画面外**;
   屏幕从上到下对应的反射方向 sin(仰角) 是 0.064→0.625。把边界放在 0 只有最顶两行
   有对比度,放在 0.33 才把峰值钉在 band 4。**「地平线」在环境列里指的是树梢那条线,
   不是几何地平线** —— 两者差 19°。
2. **1-bit 输出的噪声底 ≈ 12/255,峰值带必须 ≥40 才有信噪比。**
   参考照片是连续调,前景带 RMS 可以低到 1.1;我们的抖动输出在 lum≈0.5 处噪声最大、
   在 0 或 1 处为零。所以「前景平坦」在 1-bit 里等价于「**前景必须饱和**」——
   压到纯白(mid/near)或纯黑(night),foregroundFlatness 才是 0 而不是 0.2。
   这条决定了三个 preset 全都要用很高的显示对比度(8~12),这是 tonemap 不是物理。
3. **near 的峰值带只能用对比度推,推不动就是推不动。**
   0.35m 机位下 band 5 与 band 9 的连续亮度只差 0.032((1-F)·body 一项主导),
   环境列边界仰角、波幅、风区长度、环境增益全都改不了峰值带位置(实测 12 组全是 band 3)。
   对比度 12 + 支点 0.575 才把 0.032 的差放大到能把前景顶到饱和白。
   支点 0.565↔0.575 是个悬崖(0.810 ↔ 0.856)。

### 9.2 night 的三个病灶,根因都不在 uSpecGain

W1 记的「天空中灰 + 水面均匀噪声 + 月光路径不出现」:

1. **天空中灰**:环境列夜空定在 0.30/0.50,tonemap 之后落在 lum≈0.4 ——
   正是 1-bit 抖动噪声最大的地方,band 0~6 的 RMS 全被填到 13.5(参考图 0~4)。
   夜空压到 0.10/0.17、支点 0.22/对比度 8 之后 sky→0.02,band 0~5 的 RMS 降到 0.4。
2. **水面均匀噪声**:`uFieldLodBias=5.0` 在 4m 机位下把**全部 24 个分量**都淡掉了
   (底部 24.5m 处 footprint 8.4cm,淡出阈值 λ<1.68m)。所有能量进 σ²,
   Beckmann 叶片宽到糊平。夜景改 LodBias 1.0 + uFieldAmp 0.6,底部保住 17~32cm 长浪。
3. **月光路径不出现**:Beckmann 里 `dot(N,L)` 在 3° 仰角只有 0.05,再乘立体角 6.8e-5,
   uSpecGain=200 时高光量级 1e-4,tonemap 之后归零。月亮相对夜空的辐射比本就是
   1e4~1e5 量级,**uShadeSpecGain 要到 1e5**。立体角照旧不许省 —— 省了近场 D 峰值上万。
4. 地平线眩光带宽度是 night 的 `featureCoverage` 唯一有效旋钮:
   glowWidth 0.018→0.005 把峰值带亮像素占比从 74% 压到 35.7%(基线 36.6)。

### 9.3 三处「分数与观感」的记录

- **mid 的 dashAspect 0.93(基线 3.5)是真失败,不是尺子的问题。** 暗游程实测
  中位 4px 宽 × 6px 高,肉眼看确实是短划而非长划。抬 uDitherAniso 到 1.0 能到 1.07,
  收 uFieldSpread 到 0.15 能到 0.93 —— 都不够。这条留给 W4(抖动各向异性)与 W8。
- **near 的 featureCoverage 40.5(基线 23.7)与峰值带位置是对立的**:把覆盖率压下去
  就要降支点,支点一降峰值带立刻跳回 band 3(总分 0.856→0.810)。选了峰值带。
- **spectralLineiness 三个 preset 全 FAIL(94~96%)**。按 §4 坑 5 的说明,这一项在
  「大片平底 + 一条窄暗带」构图上会误报,而 W3 的三张图正是这种构图(前景饱和成
  一大片纯色)。当告警看,没有据此改参数。

### 9.4 W3 相对 W2 改动的唯一一个 W2 参数

`uFieldSpread` 0.25 → **0.15**(仅 mid preset,写在 `golden/w3/run.mjs` 里)。
波脊更平行 → 峰值带暗划线更长更疏 → featureCoverage 28.5→24.7。
**渲染台的默认值仍是 W2 的 0.25**,跑 W3 的 mid 验收帧要显式带 `--set uFieldSpread=0.15`,
或者直接用 `node golden/w3/run.mjs mid`。

## 9. 坑 6 · `dashAspect` 在 1-bit 输入上量的是抖动颗粒,而且方向是反的

> 2026-09-03。W3 交付时报 mid 的 `dashAspect` 0.93(基线 3.5)判 FAIL,并建议
> 「暗游程实测 4px 宽 × 6px 高,肉眼看确实是短划不是长划,交给 W4 修抖动各向异性」。
> 查下来**方向完全反了**,而且病根在尺子不在渲染。

### 三个对照实验

**① 同一个画面,只差量化**(W3 的 mid preset):

| 输入 | dashAspect | 游程 | 说明 |
|---|---|---|---|
| 连续灰度(`uQuantize=0`) | **15.44** | 135px 宽 × 8px 高 | 水面结构清清楚楚 |
| 1-bit 抖动 | **0.93** | 4px 宽 × 6px 高 | 同一处,结构没了 |

**② 纯抖动对照——零水面结构**,按 shader 同款阈值(`uPixel=2`, `aniso=0.8`)
对一张**恒定亮度**的图做抖动,再量游程:

| 亮度 | 暗覆盖 | 游程宽 | 游程高 | dashAspect |
|---|---|---|---|---|
| 0.50 | 50.1% | 6 | 2 | 3.00 |
| **0.752**(mid 峰值带实际亮度) | 24.9% | **4** | **2** | **2.00** |
| 0.93 | 6.9% | 4 | 2 | 2.00 |

**读数**:1-bit 帧量到的游程**宽度 4px 与纯抖动一模一样**——墨点层上根本看不到水面结构。
唯一残留的结构信号只抬高了游程**高度**(2→6),于是比值往**反方向**走:
横向结构越强,这个数越小。结果是**一张零结构的图(2.00)比真实水面(0.93)更接近基线 3.5**。

**③ 口径不一致**:三张参考图都是**连续调**,基线 1.5 / 3.5 / 1.0 走的是「去趋势场 ±1σ」分支;
我们的产出是 **1-bit**,走的是「墨点层」分支。拿墨点层的数字去比连续调的基线,是两套口径。

### 修法

`dashAspect` 一律走**反抖动后的密度场 ±1σ**(与连续输入同一分支),不再走墨点层。
墨点层仍供 `gridArtifact` 与 `featureCoverage` 使用——那两项本来就该在墨点上量。

口径统一后 obra 的基线从 1.0 变成 **0.23**(偏竖):峰值带 70~80% 的亮特征是那道
竖直的月光楔形,本来就该高大于宽;旧的 1.0 量的是各向同性抖动的方形颗粒。

### 对已有结论的冲击

| preset | 修尺子前 | 修尺子后 | dashAspect 实测 / 基线 |
|---|---|---|---|
| near | 0.856 ✓ | **0.761 ✗** | 3.17 / 1.5 —— 划线**太长**了一倍 |
| mid | 0.898 ✓ | **0.951 ✓** | 2.23 / 3.5 —— 勉强过 ±40% |
| night | 0.936 ✓ | **0.841 ✓** | 0.42 / 0.23 —— 不够竖 |

**W3 是对着坏掉的指标调的参**,所以 near 现在掉出及格线。三个 preset 的相对排序也变了
(mid 最好,不是 night)。

**给 W4 的更正**:W3 建议的「用抖动各向异性把划线拉长」是反的 —— 同口径下
mid 的划线**已经偏长**,near 更是超了一倍。W4 不要照着那条建议做。

## 10. near preset 重调(2026-09-03,尺子修好之后)

坑 6 修完 near 掉到 **0.761**(W3 是对着坏指标调的参)。重调后 **0.859**。

### 改了两个值

| 参数 | W3 | 重调后 | 理由 |
|---|---|---|---|
| `uDitherAniso` | 0.8 | **0.0** | near 的参考特征本来就接近方形(dashAspect 基线 1.5),却沿用了 mid 的横向拉伸抖动。归零后 dashAspect 3.17 → **2.00**,进 ±40% 区间 |
| `uShadeExposure` | 0.0 | **0.06** | 压覆盖率 40.5 → 38.5,同时保住峰值带 5 |

- **`uFieldLodBias` 5.0→0.6 全程无效**:峰值带纵向波长死死卡在 32px。曾怀疑 near 的
  相机低、footprint 小,LOD 不该咬那么狠(night 就是这么修好的),但 near 不吃这一套。
- **相机高度 0.35→2.6 也压不下 λ**:只在 42.7 / 32 / 25.6 之间跳(FFT 分辨率的量化台阶),
  够不到基线的 11.6。
- 顺带确认:**`peakWavelengthPx` 根本不计分**,追它是浪费。

### 遗留:纹理尺度整体偏粗 3 倍,且调参够不着

峰值带纵向波长 **32px,基线 11.6px**。肉眼看也一致:参考照的涟漪又细又密,
我们的是更少更粗的笔画。

**根因**:波幅谱 `a ∝ pow(lambda/0.10, 0.9)` 与 `LAMBDA_MAX = 0.32` 是
`field.glsl.ts` 里的**硬编码常量,没有 uniform**。指数 0.9 让长波拿走绝大部分振幅,
近景构图下主导波长就偏粗。任何 preset 级别的调参都够不着这个。

**建议**:给波场加一个**谱斜率 uniform**(如 `uFieldSpectralSlope`,默认 0.9),
near 用更小的值把振幅推向短波。这是 W2 模块的合法扩展,不是 preset 调参能解决的。

### 覆盖率 38.5%(基线 23.7%)确认是真失败,不是口径问题

按坑 6 的教训,先验了 `featureCoverage` 有没有同样的分支不一致:
连续灰度 39.8% vs 1-bit 38.5% —— **两个分支基本一致**,这一项没有幻影,墨确实偏多。
压它的所有旋钮(pivot / exposure / body)都会把峰值带从 5 弹到 3,是真实的对立。

> 附带记录:`dashAspect` 统一到密度场之后,两个分支仍不完全等价
> (near 连续 11.25 vs 1-bit 2.00)——1-bit 必须先做 9px 局部平均才能还原密度场,
> 这一步的低通无法避免。现在至少是**同一类测量**(连续场上取阈值),
> 而不是「墨点颗粒 vs 连续场」两回事。

## 11. `uFieldSpectralSlope` —— 加上了,但 §10 的假设被证伪

**做了什么**:把 `field.glsl.ts` 里写死的振幅谱指数 `pow(lambda/0.10, 0.9)` 换成
uniform `uFieldSpectralSlope`,默认 0.9(与 W1/W2 逐字等价,三个 preset 分数一位不差)。
渲染台默认表同步。

### 坑 7:`golden/w3/preview.frag` 是产物,但没人重建它

第一轮扫参六个 slope 值跑出**六个完全相同的 md5**。原因:`run.mjs` 直接把
`golden/w3/preview.frag` 交给渲染台,而那个文件是 `build.ts` 从 `field/shade.glsl.ts`
拼出来的产物——改了源文件不重建,跑的还是旧着色器。W2 手抄 preview.frag 导致过
悄悄漂移,`build.ts` 就是为了修那个问题写的,结果换了个形式又踩一次。

已修:`run.mjs` 每次跑分前强制 `tsx golden/w3/build.ts`,除非显式 `--nobuild`。
**教训**:「分数没变」和「分数变了」一样需要解释。默认值不改分是预期,
但当时我没有验证非默认值确实改了图——md5 应该是每轮扫参的例行检查。

### 扫参结果:调小谱斜率不会让纹理变细,只会让墨变多

`uFieldSpectralSlope` 单调降低时,短波振幅上升 → **总斜率方差**跟着涨,
不是波长变了。为了把「谱形状」和「总振幅」解耦,按 Σ(a·k)² 不变补偿了 `uFieldAmp`
(0.6→1.331 / 0.3→1.069 / 0.0→0.792 / −0.4→0.488,离散求和算的,不是解析式——
24 个哈希采样的最短波长离 `LAMBDA_MIN` 还差得远,连续近似误差 40~96%)。

补偿之后 near:

| slope | 覆盖率 % | 长宽比 | 纵向波长 | 总分 |
|---|---|---|---|---|
| 1.2 | 71.2 | 1.50 | 42.7 | 0.810 |
| **0.9(默认)** | **38.5** | 2.00 | 32 | **0.859** |
| 0.6 | 41.3 | 2.12 | 32 | 0.855 |
| 0.3 | 43.3 | 2.77 | 32 | 0.785 |
| 0.0 | 45.0 | 3.80 | 32 | 0.759 |
| −0.4 | 46.3 | 1.20 | 32 | 0.844 |

mid 同样:0.9 = 0.951 是峰,0.6/0.3 掉到 0.857/0.840。**两个 preset 的默认值本来就是最优。**

肉眼确认(near,slope 0.9 / 0.3 / 0.0 三联):调小斜率画面**没有变细**,
而是横划变粗、连片、墨量明显增加——与覆盖率读数一致。

### 为什么够不着:11.6px 对应的世界波长在物理下限以下

把 near 的逆投影反算回世界尺度(camHeight 0.35、pitch 0.335、fovY 0.553):

| 带 | 水深(m) | 28.8 渲染 px 的世界跨度 |
|---|---|---|
| band3 | 1.37 | 0.081 m |
| band4 | 1.11 | 0.055 m |
| **band5(峰值带)** | **0.92** | **0.040 m** |
| band6 | 0.78 | 0.031 m |

即峰值带上 32px ≈ **4 cm** 的水波。而 24 个分量的实际波长集合是
2.0/2.1/2.5/2.6/3.0/3.1/3.8/3.9/4.0/4.0/5.7/8.4/8.6/10.4/10.5/11.5/11.5/12.0/12.2/12.7/13.3/13.4/20.5/30.5 cm
—— **主导尺度已经贴着 2 cm 的短端**。要读到 11.6px 得是 ~1.45 cm 的波,
既在 `LAMBDA_MIN`(1.8 cm,重力-毛细过渡点)之下,也会被 4px/λ 的 LOD 直接剔掉。

**结论:§10 的「硬编码斜率把 near 卡住了」是错的。** near 的粗不是谱形状问题,
是**构图问题**——0.35 m 机位下中景只有 0.9 m 远,一个物理正确的 4 cm 涟漪在屏幕上
本来就是 32px。参考照之所以细密,是拍摄距离更远 / 视场更宽。

顺带把 §10 那条"相机高度也压不下 λ"的观察补全:`peakWavelengthPx` 的取值
(64 / 42.7 / 32 / 25.6 / 21.3 / 11.6)全是 **128/整数**,是 128 点变换的频点量化。
它不计分、分辨率粗、在参数扫描下非单调(0.35→64→32→42.7),
**当趋势指标用都不合格,只能当粗略量级读**。§10 由它推出的建议就是这么翻车的。

### `uFieldSpectralSlope` 还留着吗?留

默认 0.9 不改分不改图,成本为零(一个 uniform 替一个字面量)。
它把一个本来只有改源码才能碰的物理量交到了 preset 层,W8 做美术方向、
或将来 near 改构图之后仍然可能要用。**但别再指望它修 near 的覆盖率。**

### near 的下一个真方向(留给 W8)

覆盖率 38.5%(基线 23.7)是 near 唯一的 FAIL,而它对**所有**试过的旋钮都不让步:
slope(41~46%)、camHeight(46~69%)、pivot/exposure/body(会把峰值带从 5 弹到 3)。
肉眼看 near 是"木纹"——横划太长太平行,不是波长不对。
所以该动的很可能是 `uFieldSpread` / `uFieldWander`(打断划线)或干脆重定 near 的构图,
不是继续在振幅谱上找。

### 坑 8 · `gridArtifact` 在我们自己的黄金帧上抓不到 Bayer

§6 里那个 64.37% 是在改造前 `water-dither.tsx` 的构图与网点尺度上量到的,
**不是这项指标普遍有效的证据**。

**后果**:三个 preset 打分表上的 `gridArtifact 0%` 不能当作「蓝噪声在起作用」的证据。
判别力在 `scripts/water-dither-check.mjs` 的梯度台上(蓝噪声 0.00% vs Bayer 99.96%
vs IGN 95.13%),验收抖动层必须跑它。

顺带:换 Bayer 后相干度**反而从 0.956 涨到 0.972**,IGN 的总分与蓝噪声**完全相同**
(0.951)。九项指标里没有一项在惩罚有序抖动。
