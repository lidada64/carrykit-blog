# 本机 CLI Agent 博客助手：方向讨论

日期：2026-10-07。状态：建议，尚未确认；本轮未实现代码。

## 用户原话

> 如果设计成CLI呢?最近在学agent,能否将流程设计为一个文件管理的CLI agent助手,能帮我发送到我的博客里呢.讨论这个方向的现实考量与建议

## 结论建议

可行。采用可独立运行的确定性 CLI 工具，加单个受约束的 Agent 对话层。文件管理范围先限定为文章工作区；本机运行不等于模型本地运行，使用云模型时文稿会发送到所选服务并产生调用费用。

Agent 负责理解自然语言、建议文件分类、生成元数据、整理和翻译；程序负责路径边界、原稿保护、队列持久化、审批版本校验、鉴权、发送和重试。模型通过明确工具调用执行操作，不授予任意 shell 或全盘访问权。Markdown 正文视为待处理数据，不作为指令执行。

## 与现有博客的连接

现有文章写入是带 session 的 Server Action，没有稳定外部文章发布 API。建议在博客端增加受保护的发布入口，复用保存规则、slug 唯一校验与缓存刷新逻辑；远端提供受限、可撤销的工具凭据，具体协议待设计。不能只做一个本地脚本就假设能稳定发布，也不建议复制数据库或绑定构建生成的 Server Action 标识。

现有双语字段、前台语言切换、图片存储可复用；要补英译中、元数据生成、图片相对路径解析与发布身份记录。重复发送同一内容需返回既有结果；更新文章先检查远端是否已被修改。

## 用户体验草案

示例命令（尚未实现）：carrykit import / prepare / review / approve / publish / status / chat。命令和自然语言入口共用工具与校验规则。

对话例子：“整理 inbox 里的文章，保留原文观点，生成中英文版本，交给我审批。”助手列出候选文件、执行准备、显示差异和错误；只有符合选定模式才发送。

本机工作区保存原稿、中文稿、英文稿、元数据、图片、任务状态与事件日志。审批关联内容、元数据和资源的具体版本；审批后任何影响发布内容的变更都使审批失效。重启可恢复任务，恢复后仍校验审批和远端状态。

## 模式建议（待确认）

- 手动：用户选择每个步骤并显式发布。
- 审批：自动整理翻译并检查，用户审核具体版本后批量发送；建议默认。
- 全自动：在预先选择的目录、编辑规则和目标站点范围内自动处理发布，异常项停下，不让模型自行放宽规则。

## 现实取舍

- CLI 适合批处理、文件操作、脚本组合及学习工具调用，但长文和图片在终端审核不方便；可由 review 打开本机 HTML 预览，仍以 CLI 为入口。
- 真正难点在文件状态、断点恢复、相对图片、重复发布和远端冲突；AI 润色还需明确修改尺度。
- 文件监听和自动运行需要本机进程保持运行；关闭终端或休眠后的运行取决于后续是否安装后台服务。首版建议手动触发批次。
- 云翻译有成本、限流与失败；按文章缓存结果，限制并发、轮数、重试和预算，保留代码块与链接并验证输出结构。
- 本地文件归档与线上发布成功状态分开保存；重命名/移动先给计划和映射，原稿不默认删除或覆盖。

## 分阶段建议

1. 一个真实 Markdown 文件走通导入、双语准备、预览审批、线上发布与结果核验，再扩展为可恢复的批次。
2. 增加单 Agent 自然语言入口，调用同一组工具；学习工具 schema、状态、反馈循环、权限和人工介入。
3. 稳定后增加监听目录和限定范围内的全自动模式。

首版继续使用现有 Node.js/TypeScript 技术，不为 Agent 概念提前引入大型框架、向量数据库或多 Agent 系统；具体依赖遵守仓库审批规则。
