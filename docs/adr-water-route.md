# ADR · 水面实现路线 (W1)

- **状态**:已决定 — 2026-09-02
- **决策者**:W1 spike
- **相关**:`docs/water-reference-metrics.md`(W0 标尺)、`docs/blender-assets.md`(预渲染管线)、`docs/homepage-animation-plan.md`(HR-1~HR-10)

---

## 1. 背景

要在 `/lab/water` 做一片奥伯拉丁式 1-bit 抖动水面,并让 DOM 层的迪斯科灯球照亮它。
改造前的 `water-dither.tsx` 用 W0 标尺跑分只有 **0.274**(相干度 0.003、Bayer 网纹占
高频能量 64%、前景平坦度 0.356 方向反了)。要不要推倒重写、走哪条路线,是本 ADR 的问题。

候选:

- **A 纯实时 WebGL2 shader** —— 逆投影 + 各向异性波场 + 菲涅耳着色 + 蓝噪声抖动
- **B 预渲染循环视频 + 实时交互叠加层**
- **C 混合** —— 把波场/法线烘焙成无缝循环纹理,实时只做着色、抖动与涟漪

---

## 2. 实测

### 2.1 保真度(W0 标尺,mid 基线,1920×1080 黄金帧)

| | 改造前 | 路线 A(连续灰度) | 路线 A(1-bit 量化) | 参考图自评 |
|---|---|---|---|---|
| 前景平坦度 ≤0.15 | 0.356 ✗ | 0.067 ✓ | 0.00 ✓ | 0.065 |
| 结构张量相干度 ≥0.85 | **0.003** ✗ | 0.955 ✓ | 0.779 △ | 0.974 |
| 主梯度角 90±8 | 44.4 ✗ | 91.3 ✓ | 92.3 ✓ | 91.7 |
| 峰值所在带 ±1 | 2 △ | 3 ✓ | 3 ✓ | 4 |
| 划线长宽比 ±40% | 1.0 ✗ | 3.87 ✓ | 2.0 ✓ | 3.5 |
| 特征覆盖率 ±5pp | 20.5 ✓ | 23.8 ✓ | 21.0 ✓ | 19.6 |
| 谱尖峰度 <2% | **64.4** ✗ | 0 ✓ | 0 ✓ | 0 |
| **加权总分** | **0.274** | **0.970** | **0.760** | 1.000 |

三个 preset 的量化输出:**mid 0.760 / near 0.674 / night 0.600**。
near 与 night 未调参(相机参数直接由几何推出,着色参数沿用 mid),留给 W3 / W8。

### 2.2 相对成本(SwiftShader 软件光栅 @1920×1080)

| 着色器 | 每帧中位 | 说明 |
|---|---|---|
| 改造前 water-dither | 1090.6 ms | 4 层 fbm × 3 次差分 |
| 路线 A 完整(24 分量) | 1034.3 ms | 保真度高一个数量级,成本反而略低 |
| 路线 C 代理(波场压到 1 分量) | **244.8 ms** | 波场约占整个着色器 **76%** 的成本 |

> ⚠️ 这是**软件光栅**的墙钟时间,只能做路线之间的横向比较,不是 GPU 预算值。
> 本项目云端容器没有 GPU。真实 GPU 帧时间必须在有显卡的机器上用
> `EXT_disjoint_timer_query_webgl2` 量 —— 归 W9。

### 2.3 WebGL2 能力

`EXT_color_buffer_float` / `OES_texture_float_linear` / `EXT_disjoint_timer_query_webgl2`
在 ANGLE+SwiftShader 下均可用,浮点 FBO 与 ping-pong(W6 涟漪求解器)没有阻碍。
真机浏览器矩阵的确认仍归 W9。

## 3. 决策

**主路线 A(纯实时 shader);路线 C 的烘焙作为性能杠杆预留;路线 B 否决。**

理由:

1. **A 已经被证明够得着**。连续灰度 0.970、量化后 0.760,且**肉眼确认像水**——
   透视压缩、横向暗划线、前景平静、对比度成带,四条参考图特征全部出现。
   没有理由为了保真度去牺牲交互性。
2. **A 不比现状贵**。1034 vs 1091 ms,几乎持平。以为「物理正确 = 更贵」是错的:
   现状那 4 层 fbm 被调用 3 次求差分,本身就很浪费。
3. **C 的成本优势真实且很大**(波场占 76%),但它是**优化手段不是起点**。
   先用 A 把视觉与交互定下来,W9 若发现 GPU 预算超了,再把波场烘成
   无缝循环法线图换进去——接口不变,只换 `waterNormalRough` 的实现。
4. **B 否决**:三个 preset 要三段视频、相机与构图全焊死、灯球位置一变就得重渲。
   与 `homepage-animation-plan.md` 里滚动驱动相机高度(4.0m → 0.35m)的需求直接冲突。

**回退条件**:W9 实测 1080p 中端集显 GPU 帧时间 > 8ms 且降到 0.75× 分辨率仍超预算 →
启用 C:把 `field.glsl.ts` 的 24 分量换成一张 512² × 120 帧的无缝循环法线图,
预期把水面 pass 压到 1/4。这条不需要改契约。

## 4. 过程中的发现(比结论更重要)

### 4.1 「分数过了但图是错的」发生了三次

这是本次 spike 最重要的产出:**W0 的标尺可以被骗,每张卡的验收必须包含肉眼检查。**

| # | 分数 | 实际画面 | 根因 | 已做的修正 |
|---|---|---|---|---|
| 1 | 0.970 | 织成布纹的**周期性点阵** | 6 个固定正弦的干涉是周期的;相干度/游程/梯度角全都看不出周期性 | 波场改成 24 个哈希决定波长/方向/相位的分量;给标尺加第 9 项 `spectralLineiness` |
| 2 | 0.952 | 满屏**规律重复的大墨块** | 自己写的 void-and-cluster 阶段 3 取反了(该取能量最小的 0 像素,取成了最大),后半程秩全挤成团 | 修正阶段 3;自检从单一阈值 0.5 改成 5 个阈值都测——0.5 附近正好看不出这个缺陷 |
| 3 | — | 量化后相干度从 0.95 崩到 0.34 | 抖动噪声淹掉了水面结构 | 见 §4.2 |

**给后续每张卡的硬性要求**:PR 里除了分数表,必须附黄金帧本身,并且提交人要真的看过。
分数只能证伪,不能证真。

### 4.2 抖动的选择决定量化后还剩不剩结构

这不是化妆品级别的选择。评分器(以及人眼)要从 1-bit 图里读出水面,靠的是局部平均;
这一步等于对抖动噪声做低通:

| 抖动 | 9×9 局部平均后残余 | 后果 |
|---|---|---|
| Bayer 8×8 | 低频干净 | 但能量堆在网格谐波 → 满屏十字纹,谱尖峰度 64% |
| IGN(被 `floor(frag/uPixel)` 粗化后) | — | 斜向布纹,谱尖峰度 76% |
| 哈希白噪声 | **≈11.3 灰阶** | 前景水面的起伏只有几个灰阶,直接被淹掉:相干度 0.95 → 0.34 |
| void-and-cluster 蓝噪声 128² | **3.4~4.2 灰阶** | 结构留得住:相干度回到 0.78~0.90 |

`scripts/gen-blue-noise.mjs` 现在把这个数字作为自检直接打印出来。

### 4.3 菲涅耳给不出参考图里那道断崖

前景平坦度靠 `lum = (1-F)·水体 + F·(环境+高光)`,F0=0.02 —— 前景视角陡 → F≈0.03 →
只剩平坦的水体色。这条链是对的,但只能把前景平坦度压到 **0.22**。

实拍中景照片的分带 RMS 在 band5→6 之间掉了 **10 倍**,菲涅耳这种平滑曲线给不出这种断崖。
补上**风区(fetch)衰减**——近岸被挡风、波长起不来,`smoothstep(0, uFetchLen, depth)` ——
之后掉到 0.06。近岸那条静水带是真实存在的,不是艺术加工。

### 4.4 两个把整块工作卡住的低级 bug

- **波沿错误的世界轴传播**。`uWindDir=0` → 波沿世界 x 变化 → 波脊沿 z 排列 →
  在屏幕上是**向灭点收敛的竖线**,不是横纹。要 `uWindDir=π/2`。
- **域扭曲的频率比强度重要**。第一版在 `p*0.7`(米级)上采样噪声,把 `uWarp` 从 1 加到 9
  几乎没有区别——因为它只是整片平移波场。改到 `p*4.0`(~0.25m,几个波长的尺度)才开始
  打断波脊。而真正决定划线长度的其实是**方向散布** `uSpread`,不是扭曲。

### 4.5 标尺本身修了四处

跑分过程中发现并修正的(全部已回写 `docs/water-reference-metrics.md`):

1. 整带 RMS 会被一条窄亮的月光路径带偏 → 改用每列 RMS 的 40 分位数
2. 对 1-bit 图直接算局部 RMS 量到的是抖动噪声 → 先反抖动还原密度场
3. **缩放后再做 1-bit 判定会失效** → 判定与反抖动改在原生分辨率上做
4. bilevel 时按「少数色调」自动猜墨点侧会猜反 → 改为听 baseline 指定的 polarity

第 3、4 条是给量化输出打分时才暴露的,改造前只跑参考图看不出来。

## 5. 后果

- W2 直接继承 `spike-a.glsl.ts` 的波场部分(24 分量 + fetch + 解析 LOD + σ²),
  按契约拆成 `field.glsl.ts`。**已知待办**:量化后相干度 0.78,离 0.85 还差一点。
- W3 继承菲涅耳分层 + 环境列 + Beckmann。**已知待办**:near / night 两个 preset 未调参
  (0.674 / 0.600),night 的月光路径没打出来,需要重调 `uSpecGain` / `uLightOmega` /
  环境列夜间参数。
- W4 的蓝噪声资产**已经做完**(`scripts/gen-blue-noise.mjs` + 64²/128² 两张图),
  W4 只剩:接站点色 token、各向异性阈值调参、时间稳定性验证。
- 第 9 项指标 `spectralLineiness` 目前**判别力偏弱**(点阵 29% vs 参考 16~22%),
  而且在「大片平底 + 一条窄暗带」这类构图上会误报(本次 mid 量化帧报 88%)。
  权重只给 0.05,当告警不当门槛;W8 若有余力可换成二维功率谱的方向-径向分解。

## 6. 没有测的东西(不要当成已知)

- **路线 B 与 C 没有做成独立原型**。B 的保真度上限取决于 Blender 离线渲染,而
  `ball-waterlight` 等资产尚未产出;C 的成本用「把波场压到 1 分量」做了代理测量,
  但烘焙纹理的显存占用、循环周期、法线精度损失都没量。若将来真要启用 C,需要补一次 spike。
- **真实 GPU 帧时间**。见 §2.2。
- **`npm run build`**。云端容器的出口白名单挡掉了 `binaries.prisma.sh`,
  `prisma generate` 拉不到引擎,因此 Next.js 构建无法在此验证。
  **合并前必须在本机跑一次 `npm run lint && npm run build`。**
  本次改动只新增了 `scripts/` 与 `src/components/lab/water/*.glsl.ts`(纯字符串导出),
  没有触碰任何被现有页面 import 的模块。
