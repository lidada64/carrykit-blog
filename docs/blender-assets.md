# Blender 资产铺垫与复用性 (Blender Asset Foundation)

> 路线:**路线 2 — Blender 预渲染**。所有 3D 资产在 Blender 建模 + 渲染,导出为**透明背景**的图像序列 / sprite / alpha 视频,前端用 GSAP + CSS 编排。
> 服务对象:[`docs/homepage-animation-plan.md`](homepage-animation-plan.md)(主页动画)+ 未来 radar 等页面。
> 核心策略:**一次搭好"主控场景",让灯球的模型/灯光/材质/HDRI/渲染预设可被后续所有 3D 资产复用**。

---

## 0. 资产管线(所有资产统一流程)

```
Blender 主控场景(模型 + 灯光rig + HDRI + 材质库 + 渲染预设)
      │  (Cycles 离线渲染, Film 透明)
      ▼
透明背景帧序列 (PNG, 直出 @2x)
      │  (打包/转码)
      ▼
交付前端: ① sprite sheet(.webp, CSS background-position 步进)     ← 主用,兼容性最好
          ② webm VP9-alpha + Safari HEVC-alpha 回退              ← 帧多/体积大时用
      │
      ▼
前端序列播放器(无缝循环 + scroll 变速) + CSS 发光叠层
```

### B-4 · `ball-waterlight`(水面照度序列)—— 规格

> 服务对象:`docs/water-orb-coupling.md` §6 的**模式 B**。
> **这张资产还没渲。** 前端已经把接口留好(`uOrbLightMode = 1`),
> 纹理缺失时自动回落到模式 A(程序化),不会黑屏、不会报错 —— 所以它不阻塞上线,
> 但没有它就没法验收"A/B 同帧亮度分布相关 ≥0.7"那一条。

**场景**

- 与 **B-2 `ball-loop` 同一个摄像机、同 120 帧、同无缝循环**。帧号严格对应:
  前端用 `floor(spinPhase * 120)` 取帧,差一帧就会和球的自转脱相。
- 球**正下方**放一块水平平面(足够大,见下面的覆盖范围)。
- **只渲这块平面接到的光**:球体、星环、灯具全部设 Holdout / Indirect Only /
  不可见,让 Cycles 只算平面上的光斑。
- **透明背景**(Film > Transparent)。输出**单通道亮度**即可(前端按 `.r` 采样)。

**必须与前端逐字一致的三个数**(不一致 A/B 切换会跳变 —— 计划 §6 列的三个翻车点之一):

| 量 | 值 | 前端的唯一定义处 |
|---|---|---|
| 镜片数 | **64** | `orb-light.ts` 的 `DEFAULT_ORB_LIGHT_CONFIG.facetCount` |
| 镜片排布 | **球面 Fibonacci 点阵**(黄金角 `π(3−√5)`) | `orb-light.ts` 的 `orbFacetNormals()` |
| 主光仰角 | **0.95 rad(54.4°)** | `DEFAULT_ORB_LIGHT_CONFIG.mainLightElev` |
| 主光方位角 | **−0.7 rad(−40.1°)**,0 = 从球的正后方(远离相机一侧)打来 | `DEFAULT_ORB_LIGHT_CONFIG.mainLightAz` |
| 镜片角尺寸 | 镜片边长 / 球半径 ≈ **0.12** | `DEFAULT_ORB_LIGHT_CONFIG.spotSpread` |
| 自转轴 | **竖直**,一个循环转满 360° | `computeOrbUniforms` 里绕 Y 轴的旋转 |

第 i 片镜子的法线(球面 Fibonacci,i = 0..63):

```
y = 1 − 2(i + 0.5)/64
r = sqrt(1 − y²)
θ = π(3 − √5)·i
n_i = (cos θ · r,  y,  sin θ · r)
```

用 Fibonacci 而不是随机点阵,就是为了让 Blender 这边**摆得出同一套镜片** ——
随机点阵每次生成都不同,A/B 永远对不齐。

**覆盖范围与打包**

- 平面要覆盖的世界范围由前端的 `uOrbLightmapRect`(minX, minY, sizeX, sizeY,
  单位米,场坐标)给出,默认 `(−8, 0, 16, 24)`。渲染时把平面做成这块矩形,
  并在交付说明里写清实际用的范围,前端照着设 `uOrbLightmapRect`。
- **512² / 帧**,12 列 × 10 行打成一张 6144×5120 的 sprite sheet
  (前端默认 `uOrbLightmapCols = 12` / `uOrbLightmapRows = 10`;行**从上往下**排)。
  体积大就降到 256²,光斑本来就是软的。
- 命名照 §E:`ball-waterlight_@2x.webp`。

**验收**(前端侧,`docs/water-orb-coupling.md` §6)

同一帧、同一球位下,模式 A 与模式 B 的亮度分布皮尔逊相关 **≥0.7**。
资产到位前这一条**未验证**,不要在 PR 里编数字。

**B-1 取舍**:接触不良闪烁有两条实现——
- (a) Blender 直接渲入 `ball-intro`:亮灭由灯光动画烘死,质感最真,但闪烁节奏不可后期调;
- (b) 只出 `ball-loop`,前端用 GSAP `SteppedEase` + CSS `brightness/opacity` 模拟闪烁:节奏可调、少一个渲染,但发光碎片不随亮灭真实变化。
→ **建议先走 (b) 快速验证观感,不满意再补 (a)**。

## E. 规格与约定(所有资产统一)

- **背景**:一律透明(Blender Film > Transparent)。
- **分辨率**:按最大展示尺寸出 @2x(retina);灯球 hero 建议 1024²–1440²。
- **无缝循环**:凡"持续旋转"资产(B-2/B-3/C-1/C-2)首尾帧必须可无缝衔接,否则 scroll 变速会跳帧。
- **帧数**:循环类 ~120 帧起,依最终滚动长度与顺滑度微调;入场类按时长×帧率。
- **交付格式**:优先 **sprite sheet(.webp)**;帧数多/体积大再用 webm-alpha(+ Safari HEVC-alpha 回退)。
- **命名**:`{asset-id}_{state}_{@2x}.{ext}`,如 `ball-loop_@2x.webp`、`ball-intro_seq/####.png`。
- **摄像机一致**:同一场景内需合成的资产(如 B-2 球 + B-3 星环)必须同摄像机、同分辨率、同中心,保证前端叠放对齐。

## F. 复用性结论

1. **主页灯球 = 全站 3D 资产的种子**。搭 M-1~M-5 主控的成本主要花在灯球上,之后 radar 的黑胶(C-2)、奖杯(C-3)等都是"换模型复用体系"的增量。
2. **主页动画本身极省渲染**:只需 B-1/B-2/B-3 三个产出,后续所有缩放/位移/咬合靠 CSS,不回 Blender。
3. **管线一次成型、处处适用**:「Blender 透明序列 → sprite/alpha 视频 → CSS 编排」对灯球、黑胶、奖杯完全一致。
4. **优先级**:先做 B-1~B-3 打通主页与管线 → 再按 C-2(音乐/黑胶,主板块+核心体验)→ C-1(品牌 motif,零成本)→ C-3/C-4/C-5 按需。
5. **风险控制**:预渲染的代价是"改样要回 Blender 重渲",故 M-1~M-5 要在第一次就把材质/打光/预设定稳,减少返工。

## F. 主控场景实建记录(2026-09,Blender 5.2 LTS)

§A 的 M-1~M-5 从"建议"变成了**实物**:`~/Documents/carrykit-blender/orb-master.blend`。
这一节记的是**建出来之后才知道的事**,规格表里没有。

### F.1 参考图与前端求解器的镜片布局**不是同一套,而且不该是**

参考图(`Disco orb.jpg`)上的球是经典镜面球:**纬度带方砖**,赤道可见半圈数出来
22~26 列 ⇒ 整圈约 44,极到极约 22 行 —— 实建取 `SEG=44, RING=22`,共 **968 块砖**。

而 `orb-light.ts` 的 `orbFacetNormals()` 是 **64 片球面 Fibonacci**。两者对不上,
**但这不是 bug**:

- **968 块砖是"看得见的球"**(B-2),决定观众看到的花纹;
- **64 片 Fibonacci 是"光的模型"**(模式 A / B-4),决定水面上 ≤24 个光斑落在哪。

它们的数量差一个量级,本来就不可能是同一套。观众也无法把某一块砖与某一个光斑
对应起来 —— 中景 48 m 外,一块砖在屏幕上不到一个像素。

**所以 B-4 渲染时不要用这颗 968 砖的球**,要另搭一组 **64 片 Fibonacci 镜面**
(同半径、同自转轴、同帧号),否则 A/B 两模式的光斑分布对不齐,
§B-4 那条「皮尔逊相关 ≥0.7」永远过不了。

### F.2 建模参数(全部实测挑的)

| 量 | 值 | 为什么 |
|---|---|---|
| `SEG × RING` | 44 × 22 | 照参考图数出来的列/行数 |
| `inset thickness` | **0.018** | 第一版 0.055,灰缝吃掉大半个面,暗砖只剩 20% 面积;参考图里暗砖占 55~65% |
| `inset depth` | 0.0032 | 再大剪影会出现明显台阶 |
| 内核球 | r = 0.985,哑光 0.02 | 堵住砖缝漏出来的洞,顺便让剪影干净 |
| 灰缝基色 | **0.30** 非金属 / rough 0.62 | 见 F.3 |
| 镜片 | 金属 1.0 / rough 0.04 | 真镜子。亮度**全靠反射到什么**决定,不靠自身颜色 |
| 星环 | 4 道,半径 1.32~1.92 R,倾角 22°,Z 偏 −8° | 照参考图的比例与姿态 |
| 相机 | 78 mm,(0, −6.2, 0.95),俯角 8° | 参考图的透视与取景 |

### F.3 一个走了弯路才想明白的地方:**高光区整片糊成白色**

第二版渲出来,左上角一整块糊成纯白,网格完全消失。

直觉是"镜片太亮",其实**根因是灰缝**:灰缝基色给了 0.85(接近白),
镜片一扫到亮面板也白 —— 两者一合并,网格就没了。参考图里那条横贯上半球的
亮带**仍然看得见格子**,说明缝与砖之间**始终有差**。

修法:把灰缝压到**中灰**,让它永远处在"黑砖"与"白砖"之间。
灰缝从此不再是亮度的参与者,只是分隔线。

### F.4 镜片要有东西可反射 —— 两块**只在反射里存在**的面板

第一版的砖几乎全黑,因为镜子照的是全黑世界。加了两块 emissive 面板,
`visible_camera = False` / `visible_diffuse = False` / `visible_glossy = True`:
**它们不进相机、不照亮任何东西,只负责被镜子照见。**

面板还必须**小而远**:第二版那块 9 单位的板离球太近,一整片镜片同时照见它
⇒ 又是一坨白。压成横向长条(scale 0.42×0.16)推到 (−7.5, −6.4, 4.6) 之后,
只有**一条**镜片带扫得到 —— 那正是参考图里那道横贯的亮带。

### F.5 自转:关键帧打在 **1 与 121**,只渲 1..120

第 121 帧 = 第 1 帧,所以 120 帧首尾相接没有跳。打在 120 上会重复一帧,
循环时能看出"卡"一下。插值必须 LINEAR。

Blender 5.x 的 Action 换成了 slotted 结构,**`action.fcurves` 没了**。
与其去趟 `layers/strips/channelbags`,不如插帧前把
`preferences.edit.keyframe_new_interpolation_type` 设成 `"LINEAR"` —— 版本无关。

星环**独立**打帧(B-3 要求它能被前端单独变速,HR-6)。

### F.6 色彩管理必须是 **Standard**

`view_transform` 不许用 Filmic / AgX:它们会把中间调压掉,而下游的 1-bit 抖动
**全靠中间调** —— 一张只有 0 和 1 的图,抖出来还是一张只有 0 和 1 的图。

### F.7 交付形态:Blender 出灰度,**量化交给 `scripts/orb-dither.mjs`**

不要在 Blender 里做风格化。灯球在 DOM 层、水在 WebGL 层,唯一能让两者读起来是
**同一种材质**的办法,是共用同一层量化:同一张蓝噪声、同一个网格(`uDitherPixel=2`)、
同一对色板(`--water-ink` / `--water-paper`)。

```bash
node scripts/orb-dither.mjs <blender_out_dir> <dithered_dir> --pixel 2 --aniso 0
```

**`--aniso` 必须是 0。** 各向异性是把阈值图在 x 向压扁让墨点连成**横划** ——
那是水面的语言(波脊是横的)。球面没有"横"的理由,开了会让球看起来在横向流淌。

## §G 灯球重建与 B-2 落地(2026-09-11)

### G.1 为什么重做

用户对 §F 那颗球提了三条:黑白比要 ~40:60、面数太少、白块要「离散但某些部位
集中,下端白多、赤道以下几乎全黑、赤道往上白又多起来」。

这三条都可以量,所以没有靠肉眼调。`scripts/orb-measure.mjs` 量参考图
(`Disco orb.jpg`,球心 (538,290) 半径 236):

| 量 | 参考图 |
|---|---|
| 整球白占比 | 42.5%(黑 57.5%) |
| 纬向瓦距 | 6.54° → RING 27.5 |
| 方瓦 → 赤道经向瓦数 | 56 |
| 下半球(瓦全黑)白占比 = grout 面积 | 34% → 瓦片边长 0.813 格 |
| 瓦级团簇 P_same(1瓦) | 0.74,拖尾到 6 瓦仍有 0.55 |
| 亮瓦占比随纬度(下→上,15° 一带) | 0.19 0.06 0 0 0 0.10 0.33 0.45 0.40 0.46 |

最后一行正是用户描述的那条曲线,数字对得上。

### G.2 关键取舍:亮瓦是反射出来的,不是涂上去的

参考图里亮瓦和 grout 是同一种白、连成一片 —— 涂白做不出这个。更要命的是,
涂白的亮斑会**跟着球转**,一眼假;真迪斯科球是亮斑留在原地、瓦片从底下扫过。

所以反解一张环境贴图:方向 s 的天空对应球面法线 `n = normalize(s − d)`,
把「该纬度要多少亮瓦」写成「该方向的天空要多亮」。全部在
`blender/orb-build.py` 里,场景从空场景完整重建(Blender 崩过一次,内存里
没存的全丢了 —— 场景必须是脚本的输出)。

六轮「渲染 → `orb-measure.mjs` → 按残差回调 coverage」收敛,抖动后各纬度带
与参考图 **RMS 1.7~2.3 个百分点**,整球白 43.0% 对 42.5%。

### G.3 路上四个坑

| # | 现象 | 原因 |
|---|---|---|
| 1 | 亮带整体下移约 17° | Blender 等距圆柱的经度是反的(`u = −atan2(y,x)/2π+0.5`),按"自然"写法生成把天空前后镜像了 |
| 2 | 曲线整体偏一档 | PROFILE 的自变量是**图上量到的**纬度,不是法线真实仰角;透视下 ψ=40° 出现在 L≈46° |
| 3 | 某条带实测在两个值之间跳 | `BETA(ψ)` 在 ψmax=80.8° 折返,照亮球**背面**的天空被折算进可见纬度箱,分位数挑中哪一半全凭运气 |
| 4 | BETA≈52° 那条带持续偏暗(要 ×1.17~1.65) | 分位数按像素个数取而不是按**立体角**;天顶附近每立体角的像素是赤道的 1/cos(lat) 倍,而那条带对应的天空正好跨过天顶 |

第 4 条把 RMS 从 7.3 一把压到 2.5,是最值钱的一条。

grout 另有一坑:它必须只对**相机光线**发亮。两种朴素写法都错 —— 对 glossy
可见会让球缘的瓦反射到自发光底球、凭空多一圈亮瓦;`visible_glossy=False`
又会让反射光线**穿过**底球打到对面天空,还是亮。正解是材质层面用
Light Path「Is Camera Ray」分流。

### G.4 B-2 `ball-loop`:48 帧,239 KB

帧数下界是**马车轮效应**定的:瓦的经向间距 6.43°,每帧转角必须明显小于它,
否则图案每帧刚好挪一格,看起来会静止甚至倒转。整圈要 120 帧,0.9 MB。

但球只要在绕 Z 转 360/SYM 度后与自己重合,循环就只需要这一段。每圈瓦数本来
就量化到 4 的倍数(为了竖缝对齐),天生满足 SYM=4;差的只是抖动场 —— 对
4 个 90° 旋转取平均即可。于是 **48 帧覆盖 90°**(1.875°/帧 ≈ 0.29 格)。

无缝性是量出来的:第 1 帧(0°)与第 49 帧(90°)最大通道差 8/255,差>2 的
通道 16 / 518400(0.003%,Cycles 采样噪声);对照相邻帧差>2 的有 33.254%。

SYM 取 4 不取 8:可见面跨约 160° 经度,90° 重复只出现 1.8 次,渲出来看不出
规律;45° 重复会出现 3.5 次,有暴露的风险。

**归一化易错**:对称化除的是 `√(SYM·JIT_N/2)` 而不是 `SYM·√(JIT_N/2)`。
SYM 个旋转样本近似独立,和的标准差是 √SYM 倍;除错了抖动幅度凭空少一半。

### G.5 流水线

```bash
# 1) 建场景(在 Blender 里跑,自动存盘到 orb-master.blend)
exec(open(r"...\orb-build.py").read())
# 2) 渲 1..48 帧到 loop/(每帧约 3.1 s,一次渲 8 帧,免得 MCP socket 超时)
# 3) 量化
node scripts/orb-dither.mjs <raw_dir> <dith_dir> --pixel 2 --aniso 0 --contrast 2.2
# 4) 打包
node scripts/orb-pack.mjs <dith_dir> public/orb/orb-loop --cols 8 --deg 90
# 5) 回测(任何时候都能跑,拿它证伪而不是证真)
node scripts/orb-measure.mjs <帧> --alpha
```

`--pixel 2` 不是 1:水面的 `uDitherPixel` 是**后备缓冲像素**,DPR 2 档位 0 时
一格 = 2 设备像素。精灵图帧宽 F 按 CSS 宽 D 显示时一格 = `2·PIXEL·D/F` 设备
像素,要等于 2 就得 `PIXEL·D = F`。球的屏幕直径由水面标定的 `radiusNdc` 定
(night 0.16 → 视口高的 16%,约 180 CSS px),所以 F=360 配 PIXEL=2。

`--contrast 2.2` 是给 Cycles 补的:水面的 lum 是着色器逐片元**解析**算的,
亚像素细节走 σ²(展宽分布)而不是求平均,所以它的中间调全是真色调;Cycles
是像素内超采样再平均,瓦片边缘那一两个像素的灰是**抗锯齿**。交付尺寸下缝宽
只有 3px、两侧各吃掉 1px 抗锯齿,实心白芯只剩 1px,直接抖会把网格啃成毛边、
整球发灰。拉对比度等于把抗锯齿带压回一个像素。

### G.6 接到页面

`src/components/home/disco-ball.tsx` 的内部渲染换成精灵图,**对外的 props 与
CSS 变量契约一字未改**(`--disco-size` / `--disco-scale` / `--disco-glow` /
`--disco-spin-duration` / `--disco-ring-duration`)—— 那正是该文件原先写好的
升级路径。星环与光晕仍是 CSS 替身,归 B-3。

精灵图只存「哪些像素是纸色」的 1-bit 掩码,颜色交给 CSS:水面每帧从 `:root`
读 `--water-ink`/`--water-paper`,主题一换水跟着换;灯球要是把色值烤进 PNG,
主题切换时水变了球不变,两层立刻不是同一种材质。已验证掩码 + 墨圆的合成与
真抖动帧在不透明区**逐像素相同**。

自转用 rAF 不用 CSS 动画:精灵图是 8×6 的二维网格,单条 CSS 动画没法同时步进
两个轴。rAF 每帧只写一个 `maskPosition`,而且**帧号没变就不写**(8 秒一圈时
实际写入 24 次/秒)。转速仍读 `--disco-spin-duration`,读的是 stage 的**行内
样式**,不是 `getComputedStyle`,不触发强制回流。
